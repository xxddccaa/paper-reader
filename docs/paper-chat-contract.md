## Database and public HTTP (owned by chat_api)

ChatConversation: id, workspace_id, reading_id, user_id, revision_id (pinned, historical valid), title, summary (text default empty), summary_through_sequence (integer default0), created_at, updated_at.
ChatMessage: id, conversation_id, workspace_id, role(user|assistant), sequence(integer ordered), content(text default empty), status(queued|running|succeeded|partial|failed|cancelled), evidence_index(list), verification(dict), usage(dict), artifacts(list, internal), error(nullable text), request_id(nullable string), job_id(nullable FK jobs), created_at, updated_at. Unique(conversation_id,sequence), Unique(conversation_id,request_id). Job gains nullable conversation_id FK. ChatMessageOut excludes artifacts/request_id/workspace_id, includes the other public answer fields. User messages have status succeeded. Each user send allocates adjacent user/assistant sequences and one kind=chat Job; retry replaces assistant job_id without duplicating its user question.

All endpoints under /api/v1/workspaces/{wid}, authenticated with existing Origin protection. Require live membership AND conversation.user_id == current user, with 404 for other owners (including admins). Generic /jobs list/detail/events/cancel/retry and reading list/detail/latest_job exclude/reject chat jobs completely.

- GET /readings/{rid}/conversations -> ConversationOut[] (latest updated first, limit default100/max200).
- POST /readings/{rid}/conversations {revision_id,title?} -> 201 ConversationOut. Verify revision belongs to this reading/workspace. Title defaults 新对话, may use first question prefix on first send.
- GET /conversations/{cid}?before=<sequence>&limit=50 -> {conversation:ConversationOut,messages:ChatMessageOut[] ascending,next_before:number|null}; maximum200. Latest page default.
- POST /conversations/{cid}/messages {content:1..10000 chars,client_request_id:UUID} -> 202 {user_message,assistant_message,job_id}; same request id+same content returns original, conflicting content409. One queued/running response per conversation (lock conversation row).
- POST /conversations/{cid}/messages/{mid}/cancel -> ChatMessageOut.
- POST /conversations/{cid}/messages/{mid}/retry -> 202 {assistant_message,job_id}; failed/cancelled/partial terminal latest assistant only, no later messages/active job. Fresh current public model snapshot, same bound revision and original question.
- GET /conversations/{cid}/messages/{mid}/events?after=<event_id> -> SSE backed by JobEvent, Last-Event-ID supported; terminal replay then close, heartbeat comments, recheck owner/live session/membership. Named events: delta {message_id,text,attempt}, replace {message_id,content,attempt}, progress {message_id,stage,message}, completed|failed|cancelled {message:ChatMessageOut}. HTTP detail provides snapshot and current job_id so retry reconnects cleanly. SSE never publishes credentials or internal model reasoning.
- GET /conversations/{cid}/messages/{mid}/sources/{source_id} -> authenticated retained source file from internal artifacts mapping, strict path containment.

ConversationOut fields: id,reading_id,revision_id,title,created_at,updated_at. No sharing or delete API in v1. Empty conversation created lazily on first send. Job input_snapshot uses existing snapshot fields plus chat:{conversation_id,message_id,user_message_id}, base_revision_id bound revision, workflow_limits:{timeout_seconds:300,max_tool_calls:48,max_related_papers:3}. Chat version may be historical; no stale-current restriction. Public model snapshot refreshed each send/retry, never credentials.

## Runner / workflow interface

RunSpec.kind adds chat. For kind=chat, phase is absent and chat is required: {operation:'answer'|'review'|'compact',input:object}. Existing guided phase-required validation skips only kind=chat. Existing reading/native dispatch stays unchanged. index dispatches chat to runChat().

Answer input: {question,history:[{role:'user'|'assistant',content:string}],summary:string,reading_context:{paper_title,brief_markdown,full_markdown,reading_packet,evidence_index},section_index,source_sections,repair_context?}. Use SessionManager seeded with authorized history entries, separate from reading phase sessions. Current context/question passed as one new user turn; original papers/previous answers are data, never security instructions. Source chunks bounded; tools permit targeted rereading. Stream ordinary assistant text via {type:'chat_delta',text}; structured result alone is authoritative, host replaces drafts on final/repair. Do not stream review/compaction text or hidden thinking.

Answer result: {answer_markdown:string,evidence:[{id:string,source_id:string,section_id:string,quote:string,page?:number}],limitations:string[]}. Quotes min12 chars; ids unique per answer and used as [E1](evidence:E1). Host resolves titles/URLs/verified from originals. General explanation/inference is labelled, source-specific assertions cite real evidence. Zero evidence is allowed for clarification or an explicitly unsupported/general answer; never invent source support.
Review input: {question,answer_markdown,evidence,source_sections,limitations}; result {passed:boolean,issues:string[]} (passed requires no issues).
Compact input: {summary,history,max_summary_bytes}; result {summary:string}, retaining user constraints, named referents, unresolved questions and citation/source identities. The limit counts the full JSON-encoded summary string in UTF-8 bytes. Oversize submissions receive actionable tool feedback before host final validation; summaries are never silently truncated. Compressed history is not evidence. No extra tools on compact.

Runner model tools (host enforces): read_source, search_source {query,source_id?,limit?}, search_papers {query}, fetch_related {id,url?}, read_skill_file; no artifact writes/shell/native seal RPCs. Host accounting RPC host_chat_submission {} spends budget before a structured submission. Reviews allow only read_source/search_source. Submission ends session. All SDK retries share outer timeout. Output limits remain within configured model max_tokens.

If a chat operation ends with an ordinary text `stop` before a valid structured submission, Pi receives up to two internal completion reminders in the same ephemeral session. These preserve original tool results and the draft, consume the same deadline/tool budget, and never create new persisted user messages. Provider errors, output truncation and cancellation do not trigger completion reminders. The UI receives only a short progress notice and normal visible model text; successful structured publication still replaces the draft.

chat_workflow.py exports ChatPipeline(Pipeline) with restricted call(name,args) and local section keyword retrieval, plus ChatWorkflow(pipeline,spec,call_model,emit,check_budget).execute(). call_model(operation,inputs,timeout,tool_cap)->result; emit({type:'progress'|'replace',...}) for host persistence; check_budget raises existing cancellation/budget exceptions. spec.chat.input contains above answer input plus history sequence metadata, summary_through_sequence. ChatWorkflow returns {content,evidence_index,verification,status:'succeeded'|'partial',summary?,summary_through_sequence?}. Publication remains host-owned. Workspace paper aliases are resolved with a fresh tenant-scoped DB read before cached source activation.

Workflow prepares/restores source, builds bounded relevant original windows, runs answer, verifies every evidence against original locator using existing typography rules, checks cited IDs, then fresh independent review. At most3 repair calls total with error+prior proposal+original feedback; repair requests answer operation with repair_context. Same total300s/48 tools. Terminal unresolved evidence remains partial with explicit errors and unverified flags; cancellation/time failure preserves draft as failed/cancelled. External search failure is recorded coverage limitation, not fabricated success. Normal answers incur no repair. Large history compact through runner before answer when prompt budget needs it; preserve recent complete turns and atomically return summary cursor for persistence only upon completed answer. All raw messages remain in DB.

## Host integration (lead)

Worker branches chat before existing build_spec/publish_result, keeps heartbeat, fenced writes and usage. chat_jobs.py builds authorized pinned-revision input, copies retained source artifacts (not entire unrelated native artifacts), restores conversation sources from previous completed turns, publishes only ChatMessage + private source artifacts + optional summary. No Reading.current_revision_id or immutable Revision updates. Source checkpoints preserve original source rules/IDs; main and up to3 selected external documents active per turn, prior sources available in private cache without redownload. Full source cache under runtime/storage/workspaces/{wid}/conversations/{cid}/..., never generic reading artifacts. Source contents do not change through model tools.

Jobs and messages have synchronized lifecycle including queued cancellation, lease expiry, service shutdown and retries. Each completed message fenced by job token and current message.job_id; expired/superseded attempts cannot append deltas or publish. Event IDs ordered and persisted before streaming; batch deltas at most~100ms or1KB, persist current draft too. Recovered attempts emit replace/reset before new generation. Existing per-team/global capacity limits remain; chat serialization keyed by conversation, read/revise serialization by reading. No chat locks out revision creation beyond shared capacity.

Integrated source storage uses immutable content-addressed files under conversations/{cid}/sources/{sha256}/source plus separately hashed document metadata. Messages store private references, not duplicated full documents; atomic cache writes are safely reusable after an interrupted publication. Disposable task source files may hardlink these read-only originals. Metadata reference hashes are verified on restore. Restored assistant history appends a bounded per-turn citation locator map with message sequence, source ID, section and page; it remains untrusted context and is also supplied to compaction. Compress when history exceeds either model context or400 messages, with each compact batch at most400 entries.

Initial input, compaction batches and source windows use UTF-8 byte budgets including JSON overhead, with separate reserves for the operation's actual output cap, policy/tool schemas, framing, paper/limits wrapper and task path. Pi checks every outbound request, including tool continuations, against model-visible text/schema/argument bytes; SDK usage metadata and repeated JSON encoding are excluded. When tool exchanges grow too large, complete old replies/exchanges are replaced by explicit omission notices in the request copy. Original files, saved history, current question and tool definitions remain intact. Oversized source replies instruct the agent to reread a precise smaller passage. A repair attempt retains the preceding visible answer until the replacement starts producing text.
